Replication
  -- Data is going to replicated in multiple servers
  -- Data redundancy and eventual consistency
  -- High Availability
  -- Reporting
  -- Data protection -- Disaster Recovery
  -- Increase the number of servers who can handle the reads

Replica Set
  -- Maximum 50 members
  -- Maximum of 7 voting members
  -- Best practice -- odd number of members

Member
  -- Server (mongod deamon server)
  -- Priority
  -- Voting Power
  -- State
  -- Health

n member replica set
  -- Each and every member is going to exchange a heartbeat with every other members
  -- every 2 seconds there is a heartbeat exchange
    -- continuous communication that the member is alive
  -- if for 10 secs, there is no heartbeat, that member is down
  -- Times are configurable

Replica set
  -- Only One Primary
  -- Secondary members
  -- 1 Arbiter(Optional)

Priority :
  Possible values : 0 to 1000
Votes 
  Possible values : 0 or 1
Primary member
  -- Member who will handle all the reads and writes
  -- Only member who can handle the writes
  -- Priority > 0
  -- Votes :1

Secondary member
1. Normal secondary 
  -- Asynchronously Sync data from the primary
  -- Priority > 0
    -- Can become the primary if an election occurs
  -- Votes :1 or 0

2. Zero Priority Secondary:
  -- Asynchronously Sync data from the primary
  -- Priority = 0
    -- Can never become the primary 
  -- Votes :1 or 0
  -- Use case: DR, More read servers, Reporting,Dump, export

3. Hidden Secondary:
  -- Asynchronously Sync data from the primary
  -- Not Visible to the user
  -- Priority = 0
    -- Can never become the primary 
    -- If hidden, the writes may not come to this server; writes will fail
  -- Votes :1 or 0
  -- Use case: DR, Reporting,Dump, export
  -- No reads/ writes from the app will come to this member but it will have always the updated data
  -- Dump / export -- faster ; not yield to any incoming reads/writes

4. Delayed Secondary:
  -- Asynchronously Sync data from the primary but will a delay
  -- Not Visible to the user
  -- Priority = 0
    -- Can never become the primary 
    -- Alaways holds stale data based on delay time
  -- Votes :1 or 0
  -- Use case: Restore from accidental deletion, DR
  -- Example -- sync with the primary after 24 hours 
    -- Accidentally delete of a collection at 12pm ; 

Arbiter:
  -- Will not sync with the primary
  -- Will not hold any data
  -- Priority :0
    -- Never should become the primary
  -- Votes :1
  -- To take part in the election and vote


3 servers -- secondary members

Among all the members
	-- eligible set of secondary which can become the primary
		-- priority >=1

Election process
	-- One of the eligible secondary will call for the election
	-- All the voting members will vote
	-- Whichever eligible secondary has the max votes(majority) becomes the primary
	-- Eligible secondary member will vote for themselves

Synchronisation process:
	Write op 
		-- primary will add it as a doc with a write query to a special capped collection called as oplog. Execute the query in the primary
		-- Secondaries will have to sync asynchronously
		-- Each secondary may do it at a different timeline
		-- Secondary will copy the docs from the primary's oplog from the last point it has synched to the current time and add to its own oplog. Execute the oplog entries which it has appended
N1, N5 ; 
Primary:N3
		



Write concern : {w:number/majority}
	-- Number any positive number greater than 0 but less than equal to total number of members in the replica set

Write operation:
	-- Sent to the primary
		-- Find the write concern
			-- {w:1}
				-- Only one member in the replica set have to complete the write op to send a successful acknowledgement to the user
				-- primary will complete the write and ack will be sent to the user;
				-- secondaries will async sync with the primary
				-- Not a best practice
				-- Problems: Initially the salary was 1000;updating a doc with empId:101, salary:2000
					1. Read for empId:101
						If the read goes to primary -- fresh data
						If the read goes to synched secondary -- fresh data
						If the read goes to unsynched secondary -- stale data
						write N3 ; n1,n2 -- synched; n4,n5 have not yet synched
						read n1 -- salary : 2000
						read n4: -- salary : 1000
						
					2. primary has completed write; ack be sent to the user; 
						-- none of the secondaries have synced yet and primary goes down
						-- election will be triggered; another member will become primary
						-- data insertion -- will be lost; user's perspective -- data is inserted
						-- create problems with persistence
			
					

			-- {w:2} ,{w:3}, {w:n}-- Not recommended
			-- {w:majority}
				-- Majority of data bearing members should have completed the write operations in their respective servers and then only the ack will be sent to user
				-- 5 members ; n3 -- primary; majority:3
				--  Initially the salary was 1000;updating a doc with empId:101, salary:2000
				-- 3 members will have to complete the write before the ack can be sent
					-- n3 for sure , assume n1,n4 have completed the writes in the respective server, ack will be sent; And then other members will async sync
				-- Adv : No data loss; chances of reading stale data -- minimum(2 of 5 may have stale data)
				-- Disadv : Time consuming query

		-- data protection

Can I achieve full consistency
	-- Yes
		-- write concern {w:n}; n is total number of members in replica set
		-- all the members of replica set complete the write op and then the ack is sent
		-- Disadv : Time consuming -- 5 members have to complete
			-- Availability becomes a question
				-- Lets say a secondary is down. 4 of 5 nodes are up; write will be never ack till all have completed. No;writes will fail


CAP : Mongodb : AP; Eventual consistency

Read op --> driver --> knows who is the current primary, config of replica set; (reads can go to secondary or not); , tags, load, --> driver will select the best member to handle the read


write op --> driver --> {w:majority} --> send the write to n3; sec will start syncing; driver will wait for primary and 2 of sec; once 3 complete , the driver will give the ack back

Oplog
	-- Special Capped collection 
		-- Restriction on size of collection and number of docs in the collection
	-- Each member has its own oplog,and access rs.status() and rs.config()
	-- Oplog should not keep growing
	-- When the size or number reaches a threshold value -- auto delete the first few docs
	
Primary's oplog 
	-- 20gb of info
Adding a new member 
	-- Sync entire 20gb
Already a member
	-- trying to sync
	-- window which it has to sync
		-- Scenario 1: window is available in primary
			-- incremental sync
		-- One of secondaries was down for a long time -- primary's oplog has got rotated
			-- will it be able to copy from primary's oplog -- NO 
			-- will it be able to copy from secondary's oplog -- NO 
			-- DBA -- mongodump and restore/ file system copy
